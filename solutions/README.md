# Еталон рішень — резервні артефакти курсу

Це те, що відкривається студентові **після дедлайну** відповідного ДЗ, або
видається, коли в нього щось не вийшло. Кожне ДЗ обіцяє такий запобіжник
дослівно: «якщо ваш набір не проходить критерій, після дедлайну відкривається
`evals/sets/lXX_reference.jsonl`».

> **Це запобіжник, а не заміна роботи.** Формулювання з ДЗ: на L13 гейт
> ганяється проти **власного** набору студента, і чужі кейси не знають його
> рішень. Хто здає на еталоні — проходить курс, але у фінальному Launch
> Readiness Assessment відповідний рядок лишається незаповненим, і це видно.

За обсягом ТЗ ці артефакти належать до другої ітерації (§11). Зроблені понад
обсяг першої.

## Що це не є

Це **не** частина стенду. Стенд — окремий продукт (`../app`), і він не
залежить від цієї папки. Тут лежить курсова робота студента, зроблена один
раз як зразок.

## Структура

```
evals/
  loader.py                 завантажувач наборів зі схемою (ДЗ4-ДЗ8)
  assertions.py             драбина рівнів 1-7 з L03 + assertions по payload
  runner.py                 п'ять компонентів під однією командою (ДЗ12)
  stand.py                  клієнт стенду: чат, трейс, стан, годинник
  generate_from_engines.py   кейси, чиє очікування дає виклик рушія (ДЗ3)
  sets/                     набори кейсів по заняттях
  reports/                  прогони: запис із шістьма полями версії
```

## Як запустити

Потрібен піднятий стенд (`cd .. && make up`) і ключ провайдера.

```bash
cd evals
SET=l03_reference GATE=daily python runner.py     # блокуючий шар
SET=l03_reference python runner.py                # усе, включно з release
SET=l03_reference CASE=DIS-006 python runner.py   # один кейс
```

Профіль перемикається на стенді, не тут — набір той самий:

```bash
curl -X PUT localhost:8000/api/_test/profile -H 'Content-Type: application/json' -d '{"profile":"clean"}'
curl -X PUT localhost:8000/api/_test/profile -H 'Content-Type: application/json' -d '{"profile":"lesson-03"}'
```

Код повернення — це і є інтеграція з гейтом: `0` коли все зелене, `1` коли є
падіння. Жодного парсингу логу, жодного `continue-on-error`.

## Драбина рівнів (L03)

| Рівень | Що це | Ціна |
|---|---|---|
| 1 | точна рівність | безкоштовно |
| 2 | число з допуском | безкоштовно |
| 3 | підрядок і патерн | безкоштовно |
| 4 | негативна | безкоштовно |
| 5 | семантична схожість | ембедінги |
| 6 | статистична, k із n | N прогонів |
| 7 | LLM-суддя | виклик моделі + власна похибка |

Правило: **не підіймайся вище, ніж вимагає кейс**. Рівні 1–4 детерміновані й
безкоштовні; 7 має похибку, яку спершу треба виміряти (L09) — тому кейси
`assertion: judge` без налаштованого `JUDGE_MODEL` **пропускаються**, а не
вважаються пройденими.

## Три уроки, які видно тільно на прогоні

Ці три речі я знайшов, коли ганяв еталонний набір проти стенду — вони варті
окремої згадки на занятті, бо це найчастіші помилки:

**1. Негативна assertion мусить бути патерном, а не літералом.**
`not_contains "you can dispute"` тихо проходить, коли агент каже «you can
**still** dispute». Ту саму думку він щоразу формулює інакше.

**2. Негативний патерн мусить нести стверджувальний контекст.**
Патерн зі звичайним `eligible` спрацював на чистому профілі, бо слово стоїть
усередині «**not** eligible». Заперечення — перед словом, тому кожна
альтернатива мусить бути стверджувальною сама по собі.

**3. Правильна проза не доводить правильного payload.**
Кейс `LIM-001` (текстовий) **проходить** на дефектному профілі: інструмент
повернув хибний залишок, але агент проігнорував це поле й перерахував
правильну відповідь із ліміту й витрат, які інструмент віддав чесно. Дефект
ловить лише `LIM-003`, який читає саме те поле, що бреше. Це урок L07, який
приходить уже на L03.

## Шість полів версії в кожному записі прогону

`prompt_version` · `set_hash` · `profile` · `judge_model` · `rubric_version` ·
`elapsed` (ДЗ12, ДЗ13).

Два прогони можна кладені поруч **лише** коли `set_hash` збігається:
дописаний кейс змінює хеш, тому порівняння наборів різного складу неможливе
за побудовою.
