## 2. Стара публічна історія вичищена

**Було:** каталог дефектів опублікували в комміті `2932f4b`. Видалення файлів
із робочого дерева його не прибирає — `git show 2932f4b:docs/defect-catalog.md`
і далі віддавав ключ до відповідей. Пізніше та сама історія повторилася з
оверлеями, названими за ідентифікаторами дефектів.

**Доказ.** Свіжий клон опублікованого репозиторію:

```
$ git clone https://github.com/TarasFedorenkoFTV/paypilot-stand.git
$ git log --oneline
fe4b2ab PayPilot — навчальний стенд AI Quality Engineering
$ git rev-list --count --all
1
$ git rev-list --all | while read c; do
    git ls-tree -r --name-only "$c" | grep -iE \
      "defect-catalog|lesson-guide|calibration|corridors|test_defects|seed-data|walkthrough|D[0-9][0-9]\.md"
  done | sort -u
(порожньо)
$ git cat-file -e 2932f4b
недоступний
$ git log --all -S "sk-ant" --oneline
(порожньо)
```

**Прийняте рішення, а не разова прибирка:** публічний репозиторій несе **один
комміт на реліз**. Це не втрата даних — він є дистрибутивом, робоча історія
ведеться приватно. Причина конкретна: поки публічна історія накопичується,
кожна колись прибрана підказка лишається в ній назавжди. Один комміт робить
цей клас витоку структурно неможливим, і `make_public.py --check` тепер
падає, якщо коммітів більше одного.

**Статус: закрито.**

**Межа, яку треба знати.** Force-push не відкликає копії: хто вже склонував
репозиторій до 2026-09-03, має старий вміст. GitHub якийсь час віддає
недосяжні об'єкти за прямим SHA, поки не зробить збірку смiття. Бекап старої
історії — `D:\paypilot-public-history-backup.bundle`.

## 4. ТЗ 10.2 — калібрування на профільній руці

**Було:** звіт у репозиторії — склейка з ізоляційної руки (один дефект поверх
`clean`), без полів `arm`, `run_id`, `measured_at`, і без назви моделі.
Приймальний підпис під 10.2 на такому доказі неможливий.

**Доказ.** Один прохід, `run_id 20260903T094131Z`, `claude-haiku-4-5`,
2580 с, усі 24 сценарії на **профільній** руці:

```
$ python scripts/calibrate.py
...
accepted 23/24   elapsed 2580.5s
single pass: all 24 rows measured in run 20260903T094131Z.
```

**Кожен зафіксований наперед коридор витримав.** Найважливіше — там, де
цифра зрушила:

| Дефект | Ізоляційна рука | Профільна рука | Коридор |
|---|---|---|---|
| D01 | 70% | **40%** | 35–90% ✅ |
| D06 | 100% | **80%** | 70–100% ✅ |
| D08 | 90% | **100%** | 55–100% ✅ |
| D24 | 80% | **90%** | 45–95% ✅ |
| D25 | 90% | **100%** | 55–100% ✅ |

D01 впав майже вдвічі, і це очікувано: на профілі `lesson-01` разом із ним
працюють D02 і D03, а не він один поверх чистого. Саме тому рука й мала бути
профільною. Коридор витримав тому, що був широкий не з недбалості, а тому що
n=10 вужчого не дає — і це перший випадок, коли зафіксований наперед поріг
справді щось перевірив, а не підтвердив сам себе.

Попередній звіт збережено: `docs/calibration-history/report-isolation-arm.json`.

**Статус: закрито, з одним винятком — D27.**

### D27 не прийнятий

Дефект визначений як **відсутність** спана `tool.escalate_to_human`. У
прогоні він спрацював 10/10 на профілі — і **1 раз із 10 на `clean`**, тобто
агент сам, без жодного дефекту, пропустив обов'язкову ескалацію.

Доміряно окремо, 20 прогонів на `clean`: **0/20**. Разом: **1 пропуск на 30**
= 3.3%, Wilson 95%: 0.6–16.7%.

Що з цим зроблено — і чого свідомо **не** зроблено:

- **не підганяв промпт.** Правило вже сформульоване як `MUST ... without
  exception`; додавання слів — це підхід, який на цьому стенді тричі не
  спрацював, а працювало прибирання суперечності. Тут суперечності немає;
- **не оголошував коридор для `clean` заднім числом.** Це рівно та помилка,
  за яку раунд 1 забракував увесь приймальний скрипт;
- **не переганяв, доки не позеленіє.** Один прогін — один результат.

Замість цього дефект лишається **не прийнятим**, а лектор отримує заміряне
число й спосіб роботи: показувати як різницю частот (5 прогонів на `clean`
проти 5 на профілі), бо одна відсутня ескалація не доводить нічого.

**Рішення замовника (2026-09-03): лишити не прийнятим.** Критерій «0
спрацювань на `clean`» не змінюється. D27 записаний як **оголошений виняток**
у `profiles/corridors.yaml` — це не робить його прийнятим, звіт і далі рахує
його провалом. Що це дає: майбутній прогін із результатом 23/24 читається
однозначно, а нова поломка одразу видна окремим рядком
`!! UNEXPECTED failures`.

Дефект лишається в профілі `lesson-09` і подається як навчальний матеріал:
тема заняття — заміряти похибку інструмента, перш ніж йому вірити, і тут це
той самий випадок на самому стенді.

## 5. Docker-шлях і Phoenix

**Було:** README пропонує `docker compose up --build -d` першим варіантом, а
Phoenix на 6006 як UI трасування. Ніхто цього не запускав — усе перевірялося
через uvicorn. Твердження «трейси дзеркаляться в Phoenix» лишалося заявою.

**Доказ.** Збірка з опублікованого дерева, помилок нуль:

```
$ docker compose up --build -d
$ docker compose ps
phoenix   Up   0.0.0.0:6006->6006/tcp
stand     Up   0.0.0.0:8000->8000/tcp

$ curl localhost:8000/health
{"status":"ok","profile":"clean","provider":"anthropic","otlp":true}

$ curl -o /dev/null -w "%{http_code}" localhost:6006
200
```

`otlp: true` означає лише, що ендпоінт налаштований, тому окремо перевірено,
чи трейси **доходять**. Один живий запит, далі запит до Phoenix:

```
$ curl -X POST localhost:6006/graphql -d '{"query":"{ projects { edges { node { name traceCount } } } }"}'
{"data": {"projects": {"edges": [{"node": {"name": "default", "traceCount": 1}}]}}}
```

У логах контейнера — жодної помилки експорту.

**Томи переживають рестарт**, тобто порада «контейнер на студента з окремими
томами» має під собою основу:

```
$ curl -o /dev/null -w "%{http_code}" localhost:8000/api/_test/traces/75bc5bd8...
200
$ docker compose restart stand
$ curl -o /dev/null -w "%{http_code}" localhost:8000/api/_test/traces/75bc5bd8...
200
```

**Статус: закрито.**

## 6. Стенд не мультитенантний

Заміряно на живому стенді, двома «студентами» на одному екземплярі:

| Дія студента A | Наслідок у студента B |
|---|---|
| обрав профіль `lesson-06` | у B профіль теж `lesson-06` |
| зсунув годинник на 2026-06-01 | вікна оскарження в B рахуються від червня |
| натиснув «Скинути стан» | спір, щойно відкритий B, зник із бази |
| поставив `top_k=1`, індекс `kb_broken` | B шукає в зіпсованому індексі |
| знизив поріг згортки до 2 | у B історія згортається після другого кроку |

Ізольована лише історія діалогу за `session_id`. Це **обмеження розгортання**,
не дефект, але збій німий: вправа одного знецінює вправу іншого без жодного
повідомлення. Варіанти розгортання — в `ONBOARDING.md`, тести — у
`tests/test_shared_state.py`.

**Каталог відтворюється байт-у-байт** із `calibration-report.json` —

## 8. Чого ці докази НЕ покривають

- **Вміст оверлеїв промпту** їде в студентську збірку й від локального

  з лонгрідів дослівно (шість інших профілів — цитати, вони позначені в

- **Три дефекти (D02, D09, D18)** не заміряні живим прогоном; причини — біля
  кожного в `defect-catalog.md`.
